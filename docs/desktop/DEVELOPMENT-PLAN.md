# AutomationCAD 开发计划与进度

> 更新：2026-10-24。本文作为跨模块计划和进度索引；逐模块职责见 [`MODULES.md`](./MODULES.md)，当前限制与决策见 [`STATUS.md`](./STATUS.md) 和 [`BACKLOG.md`](./BACKLOG.md)。

## 目标与原则

1. **更新通道优先**：先把受签名、哈希校验保护的应用更新做成可在隔离 Windows 环境验收的闭环；优先利用 NSIS blockmap 差分下载降低更新流量，但差分失败必须能安全回退完整安装包。
2. **功能模块化，客户可选择**：每项产品能力有稳定模块 ID、API 兼容范围、依赖和能力声明；客户能看懂模块用途、选择启停，未启用模块不得通过 UI、IPC、Agent、RPC/MCP 或文件副作用入口绕过门控。
3. **逐步从“内置开关”演进为“按需装载”**：现有模块开关是功能门控，不等于代码已拆包、卸载或在线下载。先稳定模块边界和数据契约，再引入经签名验证的独立模块包，避免为缩小安装包而放松代码信任边界。
4. **保留数据、兼容旧工程**：停用功能不删除客户数据；升级和模块迁移须先备份、可审计、可回退。工业 PLC 的仿真/只读能力与真实连接、写入、强制操作分开治理。

## 分阶段路线

### P0 — 安全更新通道验收（最高优先级）

**已有基础**：应用内 stable/beta 通道、手动下载、非静默且需确认的安装流程、固定 HTTPS GitHub Releases 源、更新清单 SHA-512、发布者预检、NSIS blockmap 差分和完整包回退路径已落地；发布预检会核对版本清单、安装包大小/SHA-512 与 blockmap。

**下一步**：

1. 由项目维护方配置并保护代码签名证书或签名服务，固定并审查 Authenticode Subject；发布流水线缺少签名必须失败关闭。
2. 在隔离 Windows 虚拟机对 stable 和 beta 做端到端升级矩阵：正常更新、无更新、签名者不匹配、清单/哈希损坏、差分下载失败后完整包回退、断网、磁盘空间不足和安装恢复。
3. 记录两个相邻 NSIS 版本的完整包与差分传输字节数、耗时及回退原因；只有真实数据确认差分有效后，才对外宣称节省比例。
4. 建立发布前后校验清单和回退演练；发布必须由维护者明确触发，不在本计划文档或普通开发测试中自动发布。
5. 首轮试运行使用自愿加入的 beta 客户，审核通过后再升 stable；在真实差分验收前，不宣传差分节省效果。差分回退只保证下载路径，不代表应用已具备自动版本回滚；需另备恢复/重装操作手册。当前没有 canary 百分比发布或远程 kill switch，若未来增加，须先定义授权、离线行为和停止推广流程。

**完成标准**：稳定版/测试版升级均通过真实 Windows 验收；签名或哈希异常会拒绝安装；差分失败可回退完整包；安装中断后能恢复到可启动状态；版本和差分指标有可复查记录。

### P1 — 统一模块契约与客户选择体验

1. 为所有功能建立目录：模块 ID、说明、版本、API 范围、依赖、权限/能力、数据归属、占用空间、是否需要联网和停用影响。
2. 模块设置提供按用途分组、依赖解释、启用/停用影响预览、设置导入导出；新安装可选择推荐配置，升级旧安装继续保持现有默认行为。
3. 将每个模块的状态门控覆盖到 UI、主进程 IPC、命令总线、Agent/RPC/MCP、后台任务、网络和文件写入；状态缺失或 API 不兼容时默认拒绝副作用。
4. 加入模块级契约测试：关闭模块后入口不可见、直接调用被拒绝、无额外文件/网络副作用，既有工程数据保持原样；重新启用后恢复可用。

当前 Vite 构建把动态导入内联到扩展包，源码层的“按需初始化”尚不是可独立下载的代码分块。进入真正拆包前，要调整构建产物并验证 Electron `file://` 加载、CSP、离线安装及升级后的资源路径。现有元器件数据包懒加载的是 JSON 数据，不是可执行功能模块，应维持两套不同的信任与生命周期模型。

**完成标准**：客户能在设置中清晰选择已安装模块；依赖关系不会产生隐式启用；停用不会删除数据；所有已迁移模块都有对应跨入口负向测试。

### P2 — 按需安装的模块包（在 P0、P1 稳定后）

1. 先将更新/模块元数据规范化为签名清单：模块 ID、版本、最低/最高应用 API、依赖、操作系统/架构、文件哈希、大小和迁移版本。
2. 实现模块目录与本地缓存：先预览依赖闭包、下载大小和变更，再由客户确认；包落盘前验证签名与哈希，原子切换版本，失败自动回到上一个可用版本。
3. 仅加载受信任、版本兼容的模块；主进程能力采用最小权限白名单。第一阶段不允许目录中的任意远程脚本直接取得 Node/Electron 权限。
4. 支持离线导入经签名的模块包，适配隔离网络客户；在线目录与应用主更新通道分开发布和回滚。
5. 先试点少量低风险 renderer 模块的独立构建产物；只有经过 CSP/`file://`/断网与回滚验收后，才考虑引入可下载模块包。数据包（如元器件 `parts.json`）继续走现有数据包格式，不混入可执行代码发行链。

**完成标准**：单个可选模块可独立安装、更新、停用和回滚；损坏包/不兼容 API/缺依赖均在启用前拒绝；离线环境可校验并导入；卸载前明确说明数据保留或清理选项且默认保留。

### P3 — 功能包拆分与推荐配置

按客户工作流拆成可组合模块，而非按代码目录机械拆分。建议先支持“机械设计”“电气校验”“PLC 生成与仿真”“通电联调”“工厂同步”“成本报价”“Agent 自动化”“工程归档”配置模板；模板只是一次性推荐，客户仍可逐项修改。核心工作区、工程格式和安全更新能力保留为受保护基础组件。

迁移顺序建议：低风险、输入输出清楚的成本/报告与电气规则模块；然后 PLC 生成（明确仿真与真实 PLC 边界）、同步扩展和 Agent 工具；最后处理 CAD 查看、几何内核、机械校核等资源密集且跨模块共享较多的能力。每迁移一个模块，都保持旧工程数据兼容并提供降级路径。

### P4 — 建议纳入的功能改进

| 建议 | 客户价值 | 模块化落点 / 安全要求 |
|---|---|---|
| 工程升级备份与回滚 | 应用升级或模块数据迁移失败时恢复工程。 | `project.portable` / 核心迁移服务；先快照再迁移，失败事务回滚，保留可读旧格式。 |
| 模块依赖与健康检查 | 在启用前发现缺少运行时、API 不兼容或依赖未安装。 | 模块管理器；明确列出原因和修复动作，不自动安装未确认依赖。 |
| 企业离线部署包 | 满足隔离网和受控更新节奏。 | 签名的离线更新/模块清单，支持管理员镜像与版本固定；拒绝无签名或降级包。 |
| 可导出的本地诊断包 | 客户可更快提交可复现问题，同时不被动上传工程或凭据。 | 诊断模块独立启停；默认脱敏、预览文件清单、用户明确导出，不包含 token、CAD 原件或 PLC 密钥。 |
| PLC 安全操作分层 | 减少把仿真能力误当成真机安全保障的风险。 | 仿真、只读监控、写入/强制操作分别授权；真实 PLC 接入需单独显式确认、审计和厂商现场验收。 |

## 发布与工程边界

- 任何应用/模块发布、Windows 签名或真实升级都需要维护者明确安排；本计划本身不触发发布。
- 本地自动化测试、mock、仿真和 smoke 仅证明对应软件路径，不替代 Windows 签名、真实网络或真实 PLC 验收。
- PR #6 与 PR #7 保持独立，不并入本轮；本轮 Git 提交只包含本计划文档，不改写或清理其余工作树改动。
- 用户选择模块是产品功能，不代表授权、付费状态或代码卸载；商业规则、企业管理策略和在线模块目录的托管方式仍需另行决策。
