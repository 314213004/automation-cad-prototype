# 大模型压测 / B-Rep 干涉（2026-10-27）

样本：`/root/workspace/samples/step/`（第三方示例，仅内部测试用，见该目录 README 的许可说明）。

## 一、LOD / 渲染压测

环境：Linux + xvfb 1920×1200、Electron + `--use-angle=swiftshader`（**软件渲染**）、视口 canvas 292×679。
测量方法：导入完成后，在渲染进程里连续采 90 帧 `requestAnimationFrame` 间隔，取 p50/p95/max 与折算 FPS。

| 样本 | 网格 / 三角面 | 导入耗时 | p50 帧时 | p95 帧时 | 折算 FPS | JS 堆 |
| --- | --- | --- | --- | --- | --- | --- |
| `as1-oc-214.stp`（基线） | 18 / 5,040 | 5 s | 48.9 ms | 57.8 ms | 20.4 | 58 MB |
| `RC_Buggy_2_front_suspension.stp` | 211 / 492,496 | 41 s | 177.1 ms | 247.9 ms | 5.6 | 58 MB |
| `UMC-500.stp` | 341 / 430,559 | 79 s | 232.3 ms | 260.5 ms | 4.3 | 58 MB |

**结论（必须按这个口径读）**
- 三个样本在软件渲染下都是 4–20 fps，**这些数字不代表真实 GPU 机器**；能确认的是：三角形从 5k 涨到 43–49 万时，帧时从 49ms 涨到 177–232ms，与三角形数量大致线性，说明瓶颈在光栅化而不是 JS。
- 导入耗时几乎全在 STEP 解析（同一文件用 Node + occt-import-js 单跑：UMC 68s、RC_Buggy 32s），几何上传不是主因。
- JS 堆稳定在 58 MB，说明解析产物没有明显泄漏（但 `performance.memory` 只有 Chromium 有，且不含 WASM 堆）。
- 视口 canvas 只有 292×679（xvfb 下窗口偏小），像素填充量很小；真实 1080p 视口下软件渲染会更慢——所以**没有 GPU 机器，不能据此调 LOD 阈值**。
- 现有代码里已有 LOD 骨架（`viewer.ts` 的 `geometryForLod` / render ops / 视锥剔除），本次压测没有发现它失效的证据，也没有足够的对照实验（无法在真机上关掉 LOD 比较）来证明它生效到什么程度。**这条待办的下一步是：在带 GPU 的机器上跑同一脚本，并加一个 `?lod=off` 对照。**

## 二、B-Rep 精确干涉（本轮实现）

- 脚本：`spike/brep-interference/brep_interference.py`（OCP/OCC 布尔），走 XCAF 装配树取实例（含位置），AABB 只用来筛候选对，最终体积由 `BRepAlgoAPI_Common` 真算。
- 口径：交集体积 > 1 mm³ 且占较小件体积 > 0.05% 才算干涉（相邻件共面接触不算）。
- 上限：零件 > 400 或 AABB 候选对 > 30000 直接拒绝并说明（O(n²) 布尔，硬扛会假死）。
- 桌面链路：`interference:brep` IPC → `ParametricManager.brepInterference`（复用 build123d 那套 Python/OCP）→ 干涉面板显示「件数 / 候选对 / 布尔计算对 / 交接处数 / 耗时」。

### 验证

| 用例 | 输入 | 结果 |
| --- | --- | --- |
| 精确性 | 两个 100mm 立方体，X 向重叠 10mm | 交集体积 **100,000 mm³**（解析值 10×100×100，完全一致） |
| 真实装配 | `as1-oc-214.stp` | 13 件 / AABB 候选 19 对 / 布尔 19 对 / **5 处交接** / 12.0 s；最大 `rod_1 × l-bracket_1` 1,178.1 mm³（占 7.50%） |
| 真机 UI | App 内导入 as1 → 点「精确干涉」 | 面板显示汇总 + 5 行明细，角标 5，耗时 11.997 s |

### 已知限制

- `as1_pe.stp`（AP203 老样本）用 OCC 的 `STEPCAFControl_Reader` **读不出来**（`IFSelect_RetError`），而 occt-import-js 能读——两个读器容错不同。脚本会返回 `READ_FAILED`，不假装成功。
- 只支持实体（Solid）；纯曲面/面片文件返回 `NO_SHAPES`。
- 螺纹连接（螺栓与螺母）在 B-Rep 里本来就是真交集，会报出来；这属于「几何重叠」而不是装配错误，判断要靠人。
- 单进程串行布尔，341 件的 UMC-500 会超过候选上限被拒——需要按子装配分批，后续可做「按顶层装配分组并行」。

### 顺带纠正一个旧结论

之前我报告「光伏缓存堆叠单元 94 件干涉自检 0」，那个 0 是**检查脚本的漏洞**（用 build123d `Shape.intersect` 后取 `.volume`，对复合结果是 0），不是模型没问题。用新的 B-Rep 脚本一跑，机架立柱与上下横梁在角部是**实心重叠**（每处 512,000 mm³ = 80×80×80），因为那些梁是整根实心块拼的，没有做端部让位。示意模型可以接受，但**不能再说「干涉 0」**。
