# 桌面端性能基线（200 / 1000 / 3000 件）

本页只记录**实测**数据，不引用估算值。改前与改后使用同一脚本、同一运行时；原始 JSON 见 [PERF-before.json](PERF-before.json) 与 [PERF-after.json](PERF-after.json)。

## 结论先行

- 真实瓶颈是 **three.js 场景构建**与**每帧矩阵更新**，不是几何生成算法本身。3000 件场景构建 `184.63 → 42.34 ms`（-77.1%），每帧 tick `1.5007 → 0.6755 ms`（-55.0%），堆峰值 `60.72 → 38.52 MB`（-36.6%）。
- 几何内容缓存对**重复构建**有效：3000 件热构建 `8.957 → 0.851 ms`（-90.5%）；1000 件 `4.442 → 0.312 ms`（-93.0%）。
- 缓存键序列化有一次性成本：3000 件**冷构建** `13.54 → 16.06 ms`（+18.6%）。但同一次加载里热构建与场景构建的收益远大于这部分成本，最终“生成 + 建树”总耗时仍显著下降。
- 材质数从“每件一个”降为共享材质：3000 件 `3000 → 410`（-86.3%）；几何形状也按形状键共享。这是场景构建与内存下降的主要原因。
- 渲染层没有整树重建：静态节点矩阵建好后冻结，动画只写 `mover/jaw` 子树；相同轴值直接跳过。基准里 3000 件 300 tick 实际只产生 9900 次有效变换写入，而不是全量重算。

## 测量方法

```bash
cd desktop
node --expose-gc scripts/perf-baseline.mjs --out ../docs/desktop/PERF-after.json
```

脚本用生产几何生成器 `generateMachineGeometry` 与 three.js 场景构建器 `buildThreeMachine` 造 200 / 1000 / 3000 件线性装配，每规模：

1. 冷构建一次（清空缓存后首次生成）；
2. 连续热构建 5 次，取中位数；
3. 构建 three.js 场景树；
4. headless 模拟 300 tick（60 FPS 时间步长），每 tick 更新运动状态、应用轴值、更新矩阵；
5. 每 16 tick 采样 `process.memoryUsage().heapUsed`，记录峰值。

边界：这是 **CPU 侧**基线，不包含 GPU 光栅化、纹理上传和真实窗口 compositor。运行时为 Node `v26.7.0` / Linux x64，无 WebGL；因此数据适合比较“构建与变换更新”的相对变化，不能当成 Windows 实机 FPS。

## 优化项与依据

1. **几何结果缓存（LRU，16 项）**：键包含 config、process、layout 与 form layout；命中返回同一对象，克隆后同内容也命中。`clearGeometryCache()` 同时重置命中/未命中计数，避免测试与诊断跨场景污染。`bypassCache` 只给性能诊断用。
2. **three.js 资源共享**：按 `box/cylinder` 形状与 `role|color` 材质键复用 `BufferGeometry` / `MeshStandardMaterial`，`disposeThreeMachine()` 用 Set 去重释放，避免共享资源被重复 dispose。
3. **矩阵冻结 + 增量变换**：场景建完后 `root.updateMatrixWorld(true)`，非运动件 `matrixAutoUpdate=false`；每帧只改执行机构 `mover/jaw`。`applyAxisValue()` 记录 `lastValue`，相同值在 `1e-6` 容差内直接返回 `false`，不重复写 position/quaternion。
4. **运动与传感器降频**：`MachineMotion.advance()` 只推进 active 执行机构；传感器只在状态变化时重绘材质，避免每帧遍历全部传感器并改 emissive。
5. **smoke workload 动态加载**：1000 件性能 workload 移到 `electron/perf-smoke.ts`，仅在 `--headless-smoke` 内 `import()`；普通启动不再静态引入 three.js / 几何生成器。

## 不是瓶颈 / 未覆盖

- **几何生成算法本身不是主瓶颈**：3000 件冷构建仅约 16 ms，场景树约 42 ms；优先修场景构建与每帧写入是正确的。
- **GC 不是主因**：堆峰值随共享材质与增量写入下降，但 tick 时间下降主要来自避免矩阵/材质重写，而不是更激进的手工 GC。
- **未测 GPU / WebGL 帧率**：headless 无 GPU，不能据此判断 Windows 实机 draw call、纹理带宽或 compositor 表现。真实窗口 3D 仍需 `npm run check:orbit-webgl` / 截图链路另测。
- **LRU 按条数而非字节**：16 个整机几何在 3000 件规模下约占数十 MB，极端多机型切换可能仍偏高；后续可按估算字节淘汰。
- **tick 仍是 O(执行机构数)**：虽然相同值不写矩阵，但仍会遍历执行机构读取状态；3000 件时 P95 已低于 1 ms，暂不值得引入脏集合索引。
- **BOM 5,000 行与 STEP 200 MB 是硬保护，不是性能优化**：超限直接给中文拒绝原因，避免进入解析器；不同 CAD 格式的解析耗时仍需真实大文件样本。

## 复现注意

- 必须先 `--expose-gc`，否则堆峰值受上一轮对象存活影响。
- 场景构建数据为单次测量，机器负载会带来约 10%–15% 波动；结论看同机前后对比，不要跨机器比较绝对值。
- `npm run smoke` 的 `SMOKE_PERF_OK parts=1000 buildMs=… tickMs=…` 是 CI 级门槛（build < 5000 ms、tick < 50 ms），不是本页的精细基线。
