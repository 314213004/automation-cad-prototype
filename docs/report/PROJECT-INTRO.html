Why · Problem

02设计与生产之间，仍然是人在搬数据

非标自动化的交付节奏是"一单一设计"，每个项目都要重画一遍、重算一遍、重编一遍。工具链却是割裂的：CAD 出图、Excel 记 BOM、经验选型、事后核价、PLC 手工编程。割裂的成本不在软件采购，而在每一次人工转录与每一次返工。

痛点现状做法造成的后果
设计与生产脱节CAD 出图 → 打印 → 人工把零件、规格、数量敲进 Excel → 再录入 ERP / 生产系统同一份 BOM 存在 2–3 个版本；漏项、错规格在装配阶段才暴露；图纸改了 BOM 没跟着改，采购按旧版下单。
选型靠经验气缸、导轨、断路器按老师傅经验或上一台机器照抄，参数不复核选大了浪费成本，选小了现场改；新人无法复用判断，方案质量随人波动。
成本事后才算设计完成后把 BOM 发给采购询价，几天后拿到报价再决定改不改报价周期长，方案在最后一刻被成本推翻，返工集中在最贵的阶段；同类项目之间没有成本可比性。
PLC 程序重复劳动每个项目的点位表、变量命名、气缸动作逻辑从零写或复制粘贴改命名不一致、注释缺失；调试期靠现场试错，问题定位依赖个人记忆。
外协件状态不可见委外加工的工序进度、质检结果靠电话与微信群确认交期不可预测，装配等件；出现质量问题时无法追溯到具体批次与工序。

痛点的共同结构

五个痛点看似分散，本质是同一件事：设计阶段产生的信息只有"图形"，没有"数据"。图形给人看，数据才能给系统用。只要设计成果无法被机器读取，下游的采购、加工、装配、调试就必须由人再解释一遍，解释就会失真，失真就要返工。

因此本项目的技术选择是：不去替换 CAD 的建模能力，而是在设计端把数据补齐并结构化——元件带尺寸与价格、点位带地址与类型、装配带运动学约束、设计包带清单与指纹——再用一份明确的数据契约交给生产系统。这样既不动设计师已有的工作习惯，又能让下游系统直接消费。

代价随发现阶段上升

设计阶段改一张图、动一个零件
装配阶段拆机、换件、等料
调试阶段改程序、改接线、重测

图形 → 数据

STEP 不只是预览：解析出网格树、包围盒与零件清单，成为 BOM 与干涉检测的输入。

经验 → 规则

选型、线号、载流量、干涉、受力全部固化为可执行校验，结果可复核、可导出。

事后 → 事前

成本随 BOM 实时计算，缺价项在提交前就暴露，而不是在报价之后。

三个设计取舍

  • 不重写 CAD 内核。几何解析交给成熟的 occt-import-js（WASM）与 three.js，本项目只做数据提取与业务校验，降低维护风险。
  • 契约先于接口。先定 manifest 的字段与校验规则（数量必须正整数、时间必须带时区、文件必须带指纹），再谈传输；字段错了，接口再稳也没用。
  • 幂等先于并发。同一个 zip 上传两次只入库一次，用内容指纹而不是文件名去重，避免"设计包 v2 最终版 真的最终.zip"这类混乱。

Capability · CAD

04CAD 导入与运动学标注

装配体可以直接拖进来：STEP / IGES / BREP 走 occt-import-js 解析，STL / OBJ / GLTF 走 three.js 加载。实测 424 KB 装配体（18 个零件）解析 559 ms，输出 5,040 个三角面，在普通办公机上打开即用，不需要工作站。

导入之后拿到的不是一张图

解析结果保留零件层级、每个网格的包围盒与三角面索引，因此可以直接支撑：零件树点选定位、包围盒尺寸读取、线框模式、鼠标拾取、干涉检测的初筛候选。

运动学标注：让装配体"会动"

对任意装配体标注动件 → 运动轴 → 行程 → 方向 → 缩回位 → 绑定点位，即可用滑块拖动预览 3D 姿态。中文校验覆盖动件不在 STEP 中、行程非正、点位冲突等情形；未标注时回退机型配置驱动，保证演示与实机都能跑。

这一层解决的现实问题

非标项目里，供应商给的 STEP 常常只有几何，没有装配约束。想知道"滑块走 80 mm 会不会撞到护罩"，传统做法是在 CAD 里手动拖、凭眼睛看。本项目把行程参数化：行程可被校验、被成本计算、被 PLC 点位引用，而不只是视觉动作。

Capability · Electrical Library

05电气元件库与底板布置

元件库不是一张型号清单，而是371 个型号、26 个分类，其中 219 个带可直接插入原理图的符号、191 个带真实外形尺寸。有尺寸才能排版，有符号才能出图，两者齐备才叫"库"。

底板布置画布（示意）

电箱底板按毫米坐标绘制：1 mm 吸附、两条 35 mm 导轨自动吸附、元件重叠即标红、实时统计底板利用率，结果导出 JSON 供下游复用。下图为本页排版用的结构示意，说明画布的坐标与吸附逻辑，非界面截图。

为什么 191 个真实尺寸很关键

没有尺寸的库只能用来"选型填表"，有尺寸的库才能"排布并校验"。导轨长度、模数宽、散热间距都依赖外形数据，否则底板图只能等供应商图纸回来再画。

插件化：库是长出来的

第三方元件包以 ZIP 导入，按清单校验、拦截路径穿越，启停即时影响检索与插入。新增品牌不需要改代码，也不需要重新发版。

Capability · Mechanical

07机械干涉与受力校核

干涉检测用 AABB 初筛，一次跑出候选并按严重度分级；受力校核把气缸推力、悬臂梁挠度、螺栓预紧的公式直接摆在界面上。校核结果带公式与安全系数，不黑箱。

校核项计算口径输出
干涉检测轴对齐包围盒（AABB）两两求交，重叠体积与三向重叠尺寸error / warning 分级；忽略对白名单；结果可导出
气缸推力F = p · πD²/4 · η；拉力按 0.85 系数折算推力、拉力、余量、安全系数
悬臂梁挠度σ = F·L / W，对照材料许用应力应力、安全系数、超限提示与截面建议
螺栓预紧F0 = 0.7 · σy · As预紧力、拧紧力矩参考

为什么用 AABB 而不是精确布尔运算

精确干涉需要 B-rep 布尔运算，在 WASM 环境下对 5000 面级装配体耗时长、失败率高，且对非标设计的意义有限——绝大多数碰撞是"装不下"而不是"差 0.2 mm"。AABB 初筛在毫秒级给出候选，工程师按重叠量排序逐个确认，配合忽略白名单，实际使用中误报成本远低于精确运算的时间成本。这是一个明确的工程取舍，不是能力缺失。

按重叠量排序复核

结果按三向重叠尺寸与体积排序：先看"装不进去"的大重叠，再看贴面级别的告警。28 处候选中通常只有少数需要改结构，其余确认后进白名单。

忽略对是项目决策，不是隐藏

确认无问题的零件对写入白名单，下次校核不再报；白名单随项目保存，可复查、可撤销，避免"报错了就把检测关掉"。

使用边界：AABB 结果偏保守（包围盒大于实体），可能存在误报；对薄壁、斜面配合等精细场合，仍需在三维 CAD 中复核。系统将其定位为"早期发现明显碰撞"，不替代详细设计验证。

Capability · Costing

08成本自动统计

成本不是一张手工汇总表，而是一条可重算的链路：BOM × 阶梯价 → 底板推算线缆/端子/导轨/线槽 → 人工 → 税/加成/运费。任何一项设计变更，成本立刻跟着变；没有价格的物料单列"待询价"，不猜数。

计算链路

#环节口径
1价格簿数据包形式维护：型号、阶梯价区间、价格来源、更新日期；示例价自动排除，避免把演示数据算进报价
2物料成本BOM 数量 × 对应阶梯区间的单价，按型号聚合
3底板推算由底板布置推算线缆长度、端子数量、导轨长度、线槽长度，按单位价计入
4人工按工时定额 × 工时单价，区分装配与接线
5税费与加成税率、管理加成、运费分别可配，逐项列出而非合并成一个系数
6缺价处理无价格的物料不参与合计，单独成表标记"待询价"，并计入覆盖率统计

价格簿字段

字段说明为什么必要
型号 / 厂商与元件库型号对齐的键BOM 行要能唯一匹配到价格，不能靠名称模糊匹配

阶梯价为什么要进引擎

同一型号买 1 个和买 50 个价格不同。若用单一单价，小批量项目会被低估、批量项目会被高估。阶梯价内置后，改数量即改单价，报价与采购口径一致。

价格可追溯

每条价格带来源与更新日期，报价单可以回答"这个价什么时候、从哪来的"。价格过期在界面上可见，避免用两年前的价报今天的单。

09PLC 联调与故障诊断

设计软件里直接连 PLC：Modbus TCP 客户端 + 内置仿真器，点位表与 3D 模型联动，联调序列可跑通 demo 场景（4 工位 / 12 执行机构 / 16 传感器），异常按 7 条规则给出中文诊断。

两种连接方式

真实设备走 Modbus TCP；无设备时用内置仿真器（表达式、自锁、定时器），读写统一在主进程超时控制。

设计与调试同源

点位来自设计端的 IO 规划，不是另建一份表。3D 随点位联动，减少"程序没问题、机械没到位"的扯皮。

诊断规则（7 条 + 兜底）

现象判定依据给出建议
点位读不到值连接正常但读取超时 / 返回异常码检查站号、寄存器偏移、从站使能
输出无动作输出位已置位但反馈位未变化查电磁阀供电、气源压力、接线
动作超时超出设定行程时间仍未到位查节流阀、负载、传感器位置
传感器抖动单位时间内状态翻转次数超阈值查安装松动、干扰、滤波时间
互锁冲突互斥输出同时为真查逻辑分支与手动干预
回原点失败回零序列未在限定步数内完成查原点开关、寻零方向、速度
通讯闪断连接在统计窗口内多次重建查网线、交换机、IP 冲突
兜底以上规则均不命中输出原始点位快照与时间线，供人工判断

诊断规则面向常见非标场景，输出为中文提示与排查顺序建议，不替代电气工程师判断。

Integration · Before / After

10设计交付：从"传文件"到"传数据包"

这是本项目与普通 CAD 工具的分水岭。联动之前，设计成果以文件和口头说明的形式流向生产；联动之后，一个带指纹、带清单、带版本的设计包直接落进智慧工厂的机台档案。

联动前人工链路

  • 设计完成，导出图纸 PDF 与 BOM Excel，存放在共享盘或个人电脑
  • 打印图纸交装配，Excel 由计划员手工录入生产系统
  • 图纸变更后重新发文件，靠文件名区分版本（v2 / 最终版 / 真的最终版）
  • 生产端不清楚哪份是最新，需电话确认；BOM 与图纸不一致时以谁为准靠问
  • 外协件进度靠微信询问，交期与质检结果留在个人聊天记录里
人工转录环节 3 处 · 版本判定靠文件名 · 变更影响面不可计算
›

联动后数据链路

  • 设计端一键打包：manifest + BOM CSV + 报告 PDF + 模型 GLB + 图纸 DXF
  • 经 X-Design-Key 机器鉴权上传，服务端按 zip SHA-256 幂等入库并分配版本号
  • 绑定到机台（deviceId = 机台编号 device_no），生产端在机台档案里直接看到最新版
  • 改版后上传新包，diff 自动列出 BOM 增/删/改与文件变更，旧版本可回滚下载
  • 后续（规划中）外协件工序与质检结果回传，看板可见"某机台某外协件"的状态
人工转录环节 0 处 · 版本由服务端分配 · 变更影响面可 diff
可追溯

每个包有唯一指纹、上传时间、上传者与版本号；谁在什么时候传了什么，服务端有记录。

可回滚

旧包原样保留，可下载。改错了不是"找不回来"，而是"退一个版本"。

可核对

BOM 与文件各带 SHA-256，传输损坏或内容被改动都能被发现。

Integration · API

11接口清单与数据契约

六个 endpoint 覆盖"传上去、查得到、比得出、绑得上、拿得回"。契约先定死，接口才稳——以下五条是联调中最容易出错、也最容易被忽略的地方。

方法路径用途
POST/api/v1/design-sync/packages上传设计包（multipart：deviceId + manifest + zip），指纹重复返回 duplicated:true
GET/api/v1/design-sync/packages按 deviceId / projectId 列出历史包与版本号
GET/api/v1/design-sync/packages/{id}单包元数据与文件清单（含逐项 SHA-256、大小、类型）
GET/api/v1/design-sync/packages/{id}/diff与指定版本比对：BOM 增/删/改、文件增/删/改
GET/api/v1/design-sync/packages/{id}/download下载原始 zip，用于回滚或离线复核
POST/api/v1/design-sync/bind绑定到机台或物料（DEVICE / MATERIAL），绑定后原图纸接口即可见

契约要点：五个"必须"

要点规则为什么必须
身份X-Design-Key 机器鉴权；deviceId = 机台编号 device_no桌面端不能持有用户会话；机台编号是生产侧唯一能对上的键，用项目名会撞车
时间createdAt 必须带时区（ISO 8601 偏移）无时区的时间在跨系统比对时会漂 8 小时，版本先后直接判错
数量bom[].qty 必须是正整数，字符串与小数一律拒绝下游要按数量算采购与成本；"1.5 个"在数据库里是灾难
完整性files[] 逐项 sha256 + size + kind能定位到"哪个文件坏了"，而不是只知道"包坏了"
幂等zip_sha256 唯一索引 + Idempotency-Key 双保险网络重试、误点两次不会产生两个版本；重传同一包不该变成 v2
联调结论：对方 material-flow-system 0.22.0 已实现 /api/v1/design-sync/*，30 项后端测试通过；本项目客户端在 301 项测试中包含同步用例——manifest 固定路径与 SHA-256、zip 只含约定产物、createdAt 无时区时拒绝打包、BOM 数量 1.5 与字符串 "1" 被拒绝、合法正整数原样写入。

安全与边界

  • 鉴权用机器密钥，服务端只存哈希、可吊销、可限定 deviceId 范围，与用户 Bearer 分离。
  • 单包上限 200 MB，manifest 上限 1 MB，文件数上限 500；解压前校验条目路径与总解压体积，防路径穿越与 zip bomb。
  • 写入审计日志（谁、何时、哪个机台、包指纹），与管理台审计同表。

12版本 diff、回滚与联调实测

设计变更在生产端最怕两件事：不知道改了什么，以及改错了退不回去。diff 回答第一个问题，zip 原样留存回答第二个。

版本 diff 的四个维度

维度输出生产端怎么用
BOM 新增新增行的编号、名称、规格、数量触发新增采购申请，不必重下整单
BOM 删除被移除行及原因定位核查是否已下单，避免多采
BOM 变更逐字段 from → to（规格、数量、材质）只处理差异项，减少重复劳动
文件变更新增 / 修改 / 删除的文件与 SHA-256判断图纸是否需重新下发到工位

回滚路径

服务端保留每个版本的原始 zip 与文件清单，/packages/{id}/download 可取回任意历史包。回滚不是"撤销操作"，而是"把某个历史版本重新绑定"——因为历史版本本身没有被修改，所以回滚一定是确定性的。这一点在评审中很关键：可回滚的前提是不可变。

三点需要说清楚的前提

  • 不替代三维 CAD。本平台做的是"设计数据的组织与校验"，精细建模仍在专业 CAD 中完成；STEP 是两者的接口。
  • 不做通用 EPLAN。面向非标整机的固定套路（导轨、模数、IO 点位、机台交付），因此可以把规则写死、把校验做深；通用电气设计软件不会为某一个厂的机台编号规范改契约。
  • 规则来自现场。线号规则、诊断规则、成本口径都按现有项目习惯固化，后续可按项目增补；这意味着它越用越贴合，而不是越用越别扭。

适用与不适用

适用

非标整机的方案设计与交付：需要快速出清单与报价、需要与生产系统对接、需要沉淀元件与规则的项目。尤其是同类机型反复设计、批量交付的场景，复用收益最明显。

暂不适用

需要精细曲面建模与模具设计、需要满足特定行业认证（如医疗器械注册）的场合；以及流程尚未标准化的项目——规则还没定，写进软件反而增加负担。

与"再买一套软件"的区别：采购软件解决的是"画得更快"，本项目解决的是"数据流得通"。前者按席位计价、按版本升级；后者把交付物变成结构化的、可被下游系统消费的资产，收益随项目数量累积。

P7 的现有基础与推进理由

P6 先做：成本引擎已完成，只差界面——投入最小、见效最快，直接支撑报价。

P7 次之：工具集与 RPC 通道已存在，边际成本低，能把"会用软件"的门槛降下来。

P8 再次：PLC 代码生成需要点位模型与联调数据做校验闭环，下层稳定后才可靠。

P9 最后：依赖委外方的排产与质检数据结构，需双方对齐口径，不是单方面能定的。

收益从哪里来

省的是"解释成本"

同一份 BOM 不再被三个人分别录入三次。每次转录都是一次解释，每次解释都可能失真；消除转录环节，错误率不是"降低"，而是"没有这个入口"。

省的是"返工时点"

干涉与选型问题在设计阶段发现，改动是移动一个零件；在装配阶段发现，改动是拆机重装。同样的错误，越晚发现越贵——这是前置校验的主要价值。

省的是"等待"

报价不再等采购逐项询价，成本随设计出来；外协进度不再打电话问。等待时间不体现在工时里，但体现在交期上。

沉淀的是"资产"

元件库、规则、价格簿、诊断经验都留在系统里。人员流动带走的是人，不是判断标准。

建议的试点方式

① 选 1–2 个真实项目

选结构相近、交付期不紧的项目，避免拿最复杂的首台机做验证，也避免拿最熟的机型——那样看不出差异。

② 先采集基线

记录改图次数、BOM 变更单数量、报价耗时。没有基线的收益无法证明，也无法说服下一批使用者。

③ 回填后决策

用实测替换本页目标值，再决定是否推广。若指标不达预期，也应如实记录原因，而不是继续扩大范围。

诚实边界：本页所有数值为目标值，未经试点验证。建议先在 1–2 个真实项目上试用，采集基线后回填本表，再据此决定推广范围。软件当前为 v0.2.0，适合试点，不建议直接全面替换现有流程。
